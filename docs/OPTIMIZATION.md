# Оптимизация игры в EXBO Launcher New 0.4.3

Вкладка «Оптимизация» доступна до входа в аккаунт и после входа.
Основа: [stalcraft-jvm-optimization](https://github.com/EXBO-Community/stalcraft-jvm-optimization),
коммит `b694d82d2a23efe6cc28690e95b07aae24e34453` (релиз v1.2.0, генератор профиля v1.1.2).
Профиль и алгоритм формирования JVM-флагов перенесены в Rust; лицензия MIT —
`LICENSES/stalcraft-jvm-optimization.txt`. Встроенная интеграция действует при запуске игры из этого лаунчера.

В 0.3.1 исправлена команда запуска с EXENS: служебный префикс
`ExensLauncher.exe -platform exbo stalzone.exe` остаётся целым, профиль меняет только
следующие за ним JVM-параметры. Античит запускается штатно. Версия Java и внешний
IFEO-перехватчик проверяются для вложенной Java-программы игры; при отсутствии
`java.exe` проверка версии больше не пытается запускать нативную программу с `-version`.

## Быстрый старт

1. Откройте «Оптимизация» и нажмите «Авто v1.1.2».
2. Прочитайте значения и пояснения. Для альтернативного G1-профиля доступна кнопка Aikar.
3. Включите «Включить JVM-профиль» и нажмите «Сохранить и применить».
4. Запустите игру. Изменения начинают действовать со следующего запуска; работающий процесс не меняется.

По умолчанию JVM-оптимизация выключена, в том числе в старых профилях лаунчера.
При включении память игры задаётся профилем; обычный ползунок RAM становится недоступен
и показывает, где менять память. Отключение JVM-профиля возвращает обычный ползунок RAM.
Настройка проверки файлов и открытие трея двойным щелчком сохраняются.

Автоподбор использует физическую RAM, логические потоки CPU и фактическую скорость
памяти из SMBIOS. До 2933 MT/s выбирается slow-профиль G1, выше или при неизвестной
скорости — mid. Heap: 3 ГиБ при 6 ГиБ RAM, 4 при 8, 5 при 12, 6 при 16 и выше.
При меньшем объёме исходный алгоритм предлагает 2 ГиБ, но проверка запаса RAM может
запретить применение; уменьшите heap или используйте обычный режим.
Число параллельных GC-потоков: потоки CPU минус два с границами 2…10,
но не больше числа разрешённых CPU (для одного CPU — один поток);
фоновых — половина, 1…5. Aikar подстраивает heap, потоки и PreTouch под этот ПК.
Ни один профиль не гарантирует прирост FPS: сравнивайте время кадра и стабильность.

## Импорт, экспорт и сохранение

- «Импорт JSON» принимает полный профиль этого лаунчера и плоские JVM JSON исходной утилиты,
  в том числе `examples/aikar.json`. Импорт только заполняет меню; он не сохраняет и не запускает игру.
- «Экспорт JSON» сохраняет полный профиль: JVM, переключатель включения, имя,
  адреса туннелей пяти регионов, способ поиска, исключённые группы и выбор CPU.
- «Справка → Экспорт JVM JSON» сохраняет плоский JSON для исходного JVM Wrapper.
  В нём нет сетевых переопределений и переключателя включения, как и в формате оригинала.
- «Сохранить и применить» сохраняет профиль в настройках лаунчера. Он переживает перезапуск.
- «Отменить изменения» возвращает последнюю сохранённую конфигурацию.
- «Справка → Сбросить настройки оптимизации» выключает JVM-профиль и ограничение CPU, очищает сетевые
  переопределения и возвращает автоподбор. Затем сохраните изменения.

Экспорт не содержит паролей, сессий аккаунтов, идентификатора установки или путей к играм.
Профили имеют ограничение 256 КиБ. Неизвестные поля, неверные типы, несовместимые версии,
значения за границами и недопустимые сочетания отклоняются. Пропущенные поля плоского
JVM JSON получают нулевые значения/false, как в Go-формате; обязательные диапазоны
по-прежнему проверяются. Профиль с другого ПК можно просмотреть, но при сохранении
включённой оптимизации проверяется RAM текущего компьютера.

## Совместимость и память

JVM-профиль предназначен для 64-битной Java 9, используемой игрой. Перед запуском
проверяется версия Java. Другие программы Java и глобальные параметры Windows не меняются.
Внешний IFEO-перехватчик может повторно заменить флаги: если он обнаружен, лаунчер
покажет ошибку с предложением отключить его через исходную утилиту.

К heap добавляются metaspace, JIT-кэш и запас для нативной памяти; Windows также
нужна память. Проверка требует минимум 512 МиБ запаса внутри бюджета процесса и
1024 МиБ вне него. Это нижняя проверка размера профиля, а не гарантия, что памяти
хватит при любом числе открытых приложений. Настройки не урезаются без вашего выбора.
Большие страницы требуют назначенного SeLockMemoryPrivilege, минимум 16 ГиБ RAM и
heap не больше половины RAM. Лаунчер не назначает права и не меняет политики Windows.

## Базовые функции профиля

Эти флаги формируются автоматически вместе с параметрами ниже:

- G1GC убирает мусор по регионам; Adaptive IHOP подстраивает начало фоновой разметки.
- UnlockExperimentalVMOptions разрешает экспериментальные параметры G1 из меню.
- ParallelRefProcEnabled выполняет обработку ссылок параллельно.
- DisableExplicitGC игнорирует явные запросы System.gc.
- UseBiasedLocking выключен: меняется оптимизация блокировок Java.
- DisableAttachMechanism отключает внешнюю attach-диагностику JVM.
- jdk.nio.maxCachedBufferSize ограничивает кэшируемый NIO-буфер 128 КиБ.
- JIT-кэш делится на 5% / 48% / остаток для неметодного, профилированного и непрофилированного кода.
- Xms равен Xmx: весь выбранный heap запрашивается при запуске JVM.

В интеграции флажки задают явное включение/выключение JVM-функций через +/-,
а не только наличие положительного флага, как в исходном генераторе.
Старые конфликтующие параметры заменяются только в JVM-части команды.
Classpath, JAR, главный класс, параметры игры и токен игровой сессии сохраняются.
«Справка → Показать флаги» показывает только параметры оптимизации, без команды авторизации.

## Память и потоки

### Память игры — `heap_size_gb`

Память Java для объектов игры. Больше не всегда быстрее: оставьте место Windows, текстурам и другим приложениям. Xms и Xmx одинаковы.

Диапазон: 1…64 ГиБ.

### Подготовка памяти при старте — `pre_touch`

Заранее обращается ко всем страницам heap. Может уменьшить задержки выделения памяти в игре, но увеличивает время запуска и сразу занимает память.

### Память классов Java — `metaspace_mb`

Отдельный лимит для описаний классов. Не входит в heap. Слишком маленькое значение может привести к ошибке Metaspace.

Диапазон: 64…2048 МиБ.

### Потоки GC во время паузы — `parallel_gc_threads`

Убирают мусор, когда игра приостановлена. Автоподбор: логические потоки CPU минус два, от 2 до 10. Избыток потоков тоже добавляет расходы.

Диапазон: 1…64 пот..

### Фоновые потоки GC — `conc_gc_threads`

Работают одновременно с игрой и конкурируют за CPU. Обычно половина параллельных потоков, от 1 до 5.

Диапазон: 1…64 пот..

### Большие страницы памяти — `use_large_pages`

Использует крупные страницы Windows. Нужны назначенное право «Блокировка страниц в памяти», минимум 16 ГиБ RAM и heap не больше половины RAM. Лаунчер не меняет политику Windows.

## G1 GC

### Целевая пауза GC — `max_gc_pause_millis`

Цель для G1, а не гарантированный предел зависания. Меньше — чаще сборка мусора и больше расходов CPU; больше — возможны длинные паузы.

Диапазон: 1…2000 мс.

### Размер региона G1 — `g1_heap_region_size_mb`

Heap делится на регионы. Допустимы 1, 2, 4, 8, 16 и 32 МиБ. Авто выбирает 4 МиБ до 3 ГиБ heap и 8 МиБ выше.

Диапазон: 1…32 МиБ.

### Минимум молодого поколения — `g1_new_size_percent`

Нижняя граница heap для новых объектов. Повышение может сократить частоту young GC, но увеличить работу за одну паузу.

Диапазон: 0…100 %.

### Максимум молодого поколения — `g1_max_new_size_percent`

Верхняя граница для новых объектов. Должна быть не меньше минимума молодого поколения.

Диапазон: 0…100 %.

### Резерв для перемещения объектов — `g1_reserve_percent`

Свободный резерв G1 для копирования живых объектов. Больший резерв уменьшает полезный heap, но оставляет больше места во время сборки.

Диапазон: 0…50 %.

### Допустимый неубранный мусор — `g1_heap_waste_percent`

G1 может закончить mixed GC, когда оставшегося мусора меньше этого порога. Больший порог снижает работу GC, но оставляет больше мусора.

Диапазон: 0…100 %.

### Количество смешанных сборок — `g1_mixed_gc_count_target`

Сколько mixed GC использовать для уборки старого поколения. Больше распределяет работу на несколько пауз, но откладывает освобождение памяти.

Диапазон: 1…64 .

### Начало фоновой разметки — `initiating_heap_occupancy_percent`

Начальный порог заполнения old gen для фоновой разметки. Меньше — более ранний старт. Adaptive IHOP затем подстраивает порог.

Диапазон: 0…100 %.

### Порог живых объектов в регионе — `g1_mixed_gc_live_threshold_percent`

Регионы с долей живых объектов выше порога не включаются в mixed GC. Выше — можно убрать больше мусора, но потребуется больше копирования.

Диапазон: 0…100 %.

### Бюджет RSet внутри паузы — `g1_rset_updating_pause_time_percent`

Часть целевой паузы на обновление ссылок между регионами. Меньше переносит работу в фон; это увеличивает фоновую нагрузку CPU.

Диапазон: 0…100 %.

### Размер области Survivor — `survivor_ratio`

Соотношение Eden к Survivor для переживших GC объектов. Больше число — меньше Survivor, возможен более ранний перенос в old gen.

Диапазон: 1…1024 .

### Возраст переноса объектов — `max_tenuring_threshold`

Сколько молодых сборок объект может пережить до old gen. Слишком малое значение быстрее заполняет старое поколение.

Диапазон: 0…15 GC.

### Порог обработки SATB — `g1_satb_buffer_enqueuing_threshold_percent`

Когда передавать буфер изменений графа объектов в обработку. Меньше — раньше обработка, но больше фоновых операций. Ноль не добавляет флаг.

Диапазон: 0…100 %.

### Порог горячих карточек — `g1_conc_rs_hot_card_limit`

Карточки с частыми изменениями ссылок обрабатываются отдельно. Влияет на фоновую работу G1; ноль оставляет выбор JVM.

Диапазон: 0…255 .

### Интервал обработки карточек — `g1_conc_refinement_service_interval_millis`

Пауза между фоновыми циклами refinement. Меньше — быстрее реакция и выше расходы CPU. Ноль не добавляет флаг.

Диапазон: 0…10000 мс.

### Соотношение игры и GC — `gc_time_ratio`

При 99 цель — примерно 1 часть времени GC на 99 частей работы приложения. Это ориентир адаптации JVM, не ограничитель. Ноль — настройка JVM.

Диапазон: 0…1000 .

### Динамическое число потоков GC — `use_dynamic_number_of_gc_threads`

Разрешает G1 менять число активных потоков по объёму работы. Может экономить CPU на небольших сборках.

### Объединение одинаковых строк — `use_string_deduplication`

Экономит heap за счёт одинаковых строк, но добавляет фоновую работу. В автопрофиле выключено; сравнивайте плавность в своей игре.

### Время жизни мягких ссылок — `soft_ref_lru_policy_ms_per_mb`

Удержание soft-reference кэшей на каждый свободный МиБ heap. Меньше освобождает память раньше, но кэши могут чаще строиться заново.

Диапазон: 0…10000 мс/МиБ.

## JIT и Java 9

### Кэш машинного кода — `reserved_code_cache_size_mb`

Память для JIT-кода, вне heap. Ноль означает 256 МиБ; ненулевое значение — минимум 64 МиБ. Заполнение кэша может мешать дальнейшей компиляции.

Диапазон: 0…2048 МиБ.

### Глубина встраивания вызовов — `max_inline_level`

Глубина вложенного inlining. Больше может ускорить горячие пути, но увеличить код и время компиляции.

Диапазон: 0…100 .

### Лимит горячего метода — `freq_inline_size`

Размер часто вызываемого метода, который ещё разрешено встроить. Более высокие значения увеличивают расход кэша кода.

Диапазон: 0…10000 .

### Лимит небольшого JIT-кода — `inline_small_code`

Порог размера скомпилированного метода для встраивания. Ноль не добавляет флаг. Большие значения могут раздувать код.

Диапазон: 0…50000 .

### Лимит графа компиляции C2 — `max_node_limit`

Лимит узлов внутреннего графа одного метода. Большие значения позволяют компилировать сложные методы, но требуют больше памяти и CPU.

Диапазон: 0…1e+06 .

### Запас узлов компилятора — `node_limit_fudge_factor`

Запас для графа C2. Работает вместе с MaxNodeLimit: задайте оба либо оба оставьте нулевыми; запас должен быть меньше половины лимита.

Диапазон: 0…100000 .

### Очистка кэша кода — `nmethod_sweep_activity`

Интенсивность уборки устаревшего JIT-кода. Слишком агрессивная очистка может потребовать повторной компиляции. Ноль — выбор JVM.

Диапазон: 0…2000 .

### Не компилировать огромные методы — `dont_compile_huge_methods`

Включено — JVM может оставить очень большие методы без C2-компиляции. Выключено в автопрофиле; их компиляция может увеличить прогрев.

### Предзагрузка при создании объектов — `allocate_prefetch_style`

Стратегия подготовки кэша CPU перед выделением объектов: 1–3. Ноль оставляет выбор JVM, а не принудительно отключает prefetch.

Диапазон: 0…3 .

### Серверный режим JVM — `always_act_as_server_class`

Включает выбор server-class эргономики JVM. Это не сервер игры; влияет на выбор компилятора и стартовые настройки Java.

### SSE для копирования массивов — `use_xmm_for_array_copy`

Разрешает JVM использовать XMM-регистры при копировании массивов. Эффект зависит от CPU и операций игры.

### Регистры для временных значений — `use_fpu_for_spilling`

Разрешает компилятору временно хранить значения в FPU-регистрах вместо стека, когда обычных регистров недостаточно.

### Прогрев reflection — `reflection_inflation_threshold`

Когда reflection создаёт быстрый accessor. Ноль и -1 запрашивают раннюю генерацию. Параметр относится к Java 9.

Диапазон: -1…10000 выз..

### Кэш целых чисел — `auto_box_cache_max`

Верхняя граница кэша Integer. Может сократить создание объектов, но сам кэш занимает память. Ноль не добавляет флаг.

Диапазон: 0…1e+06 .

### Приоритеты потоков Java — `use_thread_priorities`

Позволяет JVM учитывать Java-приоритеты потоков. Это не повышение приоритета всего процесса Windows.

### Политика приоритетов — `thread_priority_policy`

0 — обычная политика JVM, 1 — расширенный диапазон приоритетов. Применяется только при включённых приоритетах потоков Java.

Диапазон: 0…1 .

### Затухание счётчиков JIT — `use_counter_decay`

Включено — счётчики частоты вызовов со временем уменьшаются. Выключено — горячность методов сохраняется дольше.

### Скорость прогрева JIT — `compile_threshold_scaling`

Множитель порога компиляции: 0.5 раньше, 1 обычно, больше 1 позже. Ранний прогрев требует больше CPU в начале сессии. Ноль оставляет выбор JVM.

Диапазон: 0…10 ×.

## Сеть: туннели и измерения

Переопределения независимы от включения JVM-профиля. Для RU, EU, NA, SEA и NEA
можно указать свой `host:port`; пустое поле оставляет выбор игре. Это меняет
маршрут через Roxy, а не FPS или скорость интернета. Используйте доверенные узлы.

«Найти / измерить узлы» запрашивает официальный список региона и отправляет
по 10 свежих UDP-проб на узел с интервалом 100 мс. Одновременно измеряются
до 8 узлов. Протокол: UUID 16 байт, ответ 21 байт с тем же UUID, RTT backend
в big-endian и флаг лимита; измерение идёт на порт туннеля + 1.

Полный список доступен во вложенном прокручиваемом ListView без ограничения
20 результатами. «Начать заново» отменяет предыдущую серию. Есть отдельная
«Отмена»; смена региона также отменяет замер. Поздние ответы старой серии не
заменяют новую. Частичные и отменённые результаты помечаются предварительными.

Рейтинг перенесён из [PR #47](https://github.com/EXBO-Community/stalcraft-jvm-optimization/pull/47),
коммит `d0aa905252cab5d1c5669c4f7a17425513982293`:

- Для полного RTT берётся сумма клиентского и серверного RTT **одной пробы**.
- Режимы клиента/сервера используют соответствующую компоненту каждой пробы.
- Вес backend: клиентский RTT × коэффициент каталога + серверный RTT той же пробы.
- Медиана — середина отсортированных успешных измерений; при чётном количестве
  это среднее двух центральных значений. P90 — ближайший ранг 90-го процентиля.
- Обычная оценка: медиана + 0,5 × (P90 − медиана) + 1000 × доля неответивших проб.
- «Стабильность»: P90 + 1000 × доля неответивших проб.
- Штраф за неответившие пробы применяется во всех пяти режимах.
- Это стоимость выбора, **не измеренный пинг игры**. Меньше — лучше.

«Выбрать лучший» доступен после полного сравнения, при минимум 5 успешных
ответах у кандидата. Малоответивший кандидат может быть выбран вручную после
сравнения, но остаётся помеченным предварительным. Нет ответа/последний ответ
с лимитом подключений — выбрать нельзя. Выбор записывается в черновик;
для применения нажмите «Сохранить и применить». Смена режима пересчитывает
завершённые свежие результаты; во время замера смена режима отменяет серию.

Показаны медиана/P90/максимум полного RTT, успешные ответы/пробы, доля потерь,
последние и средние клиентский/серверный RTT. Jitter — среднее абсолютное
изменение полного RTT между соседними успешными пробами. Очень большой RTT
не обрезается в диагностике, хотя единичный выброс не определяет медиану/P90.
RTT сервера сообщается самим туннелем; локально измеряется клиентский RTT.

История до 20 проб на узел хранится до 24 часов в `optimization-tunnel-cache.json`.
Исторический кэш не участвует в выборе победителя новой серии. Кэш не входит
в экспорт профиля. Исключённые группы задаются через точку с запятой и учитываются
при следующем поиске. Во время запуска игры сетевых замеров нет. Передаются только
сохранённые `-Droxy_address_override.<region>=host:port`.

## Восстановление старого внешнего оптимизатора

В «Оптимизация → Справка» есть «Сохранить скрипт восстановления». Он встроен
в EXE и не требует старого `service.exe`/`wrapper.exe`. Сначала запустите
экспортированный файл без параметров: это только просмотр, без изменения реестра.

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\recover-legacy-optimizer.ps1
# Только после проверки полных путей:
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\recover-legacy-optimizer.ps1 -Apply
```

Имя service.exe/wrapper.exe само по себе не доказывает принадлежность программе:
проверяйте показанные пути. При `-Apply` Windows запрашивает UAC, затем скрипт
запрашивает подтверждение для каждой конкретной записи. До удаления сохраняется
резервная копия Debugger в `%LOCALAPPDATA%\ExboLauncherNew\recovery\IFEO-*.json`.
`-Apply -WhatIf` имитирует удаление, не запрашивая повышение прав.

Область — только native HKLM IFEO для `stalzone.exe`, `stalzonew.exe`,
`stalcraft.exe`, `stalcraftw.exe`, только значение Debugger с распознанным
path-only service.exe/wrapper.exe. Чужие команды, изменившиеся значения и типы
оставляются. Ключи, ACL, другие значения, подпапки реестра и файлы не удаляются.
Лаунчер не устанавливает новый IFEO-сервис и не запускает восстановление сам.

## Выбор процессоров (0.4.2)

В «Оптимизация → Процессор» включите ограничение и отметьте разрешённые CPU,
затем нажмите «Сохранить и применить». По умолчанию ограничение выключено:
планировщик Windows выбирает процессоры сам. Изменения действуют со следующего
запуска игры и не меняют уже работающую игру или сам лаунчер.

CPU 0, CPU 1 и далее — логические процессоры Windows, как в диспетчере задач.
SMT/Hyper-Threading может предоставлять два логических процессора на одно
физическое ядро; меню не делает предположений об их физическом расположении.
«Выбрать все» отмечает все доступные CPU, «Снять все» очищает выбор; сохранение
пустого ограничения запрещено. Отключение переключателя возвращает выбор Windows.
Меньшее число CPU не гарантирует прирост FPS и может снизить производительность.

Настройка работает независимо от переключателя JVM. Ограничение задаётся новому
процессу EXENS до начала его выполнения и наследуется дочерним игровым процессом
по правилам Windows. Применение не требует административных прав. После выбора
CPU кнопка «Авто» учитывает их количество при подборе потоков GC; вручную
заданные JVM-параметры самостоятельно не переписываются.

Полный профиль JSON версии 2 хранит `settings.cpu_affinity`: `null` означает
отсутствие ограничения, массив `[2, 3, 4, 5]` разрешает перечисленные CPU.
Профили версии 1 импортируются с отсутствующим ограничением. Экспорт «только JVM»
сохраняет совместимость с исходной утилитой и не включает настройку Windows;
импорт такого файла сохраняет текущий выбор CPU. Если профиль перенесён на ПК,
где выбранные CPU недоступны, измените выбор или выключите ограничение перед
сохранением/запуском. Выбор не обрезается автоматически.

Текущая реализация поддерживает одну группу процессоров Windows (до 64 логических
CPU). На системах с несколькими группами ручное ограничение недоступно; обычный
запуск без ограничения продолжает работать.

Техническая основа: [наследование маски affinity в Windows](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-setprocessaffinitymask).
